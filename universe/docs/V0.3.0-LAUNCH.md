## 2. 正式寫入開關（預設關閉）

`backend/worker/wrangler.jsonc` → `vars`：

| 變數 | 預設 | 作用 |
|---|---|---|
| `SCORES_ENABLED` | `"off"` | 關閉時 `/v1/sessions`、`/v1/scores` 回 503；遊戲維持「本分頁測試成績」，不寫任何正式資料 |
| `REWARDS_ENABLED` | `"off"` | 關閉時成績照常入榜，但不發 V幣 |

合併 main 不會開啟寫入。V幣消費一律關閉（PIN 介面只預留，回 501）。

## 3. 部署順序

1. 驗收並合併 `balloon-v-universe` 的 PR → GitHub Pages 更新大廳與 SDK；Cloudflare 自動部署 Worker（寫入仍關閉）。
2. 合併 `balloon-v-rush` 的 PR（`feature/universe-v0.3.0-launch-integration`）。
   - 兩個 PR 先後順序都安全：派對島掛鉤找不到 SDK v0.3.0 時什麼都不做。
3. 正式網站檢查：四個入口都能進入與返回；排行榜木牌、總覽、空排行榜；通行證 V幣顯示 0。
4. 確認要上線正式成績時，另開一個小 PR 把 `SCORES_ENABLED`、`REWARDS_ENABLED` 改成 `"on"`（不要在 Cloudflare 主控台直接改：下次自動部署會被 wrangler.jsonc 蓋回去）。
5. 開啟後用自己的玩家各玩一場，到 `universe/admin/` 確認成績與帳本。

不需要修改 Firebase Rules（瀏覽器仍完全不能讀寫；只有 Worker 用服務帳戶寫入）。不需要新增 Secret（管理員名單沿用既有 `ADMIN_UIDS`）。

## 4. 回復

| 狀況 | 做法 |
|---|---|
| 正式成績有問題 | `SCORES_ENABLED`／`REWARDS_ENABLED` 改回 `"off"`：立即停止寫入，已寫入的資料保留 |
| 派對島入口有問題 | `zones.js` 的 `gameUrls.adventure` 改回 `…/rpg-test/`、`universeGameIds` 拿掉 `"adventure"` |
| 整版回復 | revert 兩個 PR 的合併 commit |

## 5. 資料位置（新 Firebase `balloon-v-universe`）

`sessions/`、`scores/`、`scoreIndex/`、`leaderboards/{gameId}/{boardId}/{playerId}`、`quizProgress/{playerId}`、`wallets/{playerId}`（餘額、領獎標記、帳本在同一個節點，用條件寫入保證一致）、`adminAudit/`。

## 6. 已知限制

- 測試只在本機模擬環境（Worker 程式＋假 Firebase）進行；沒有獨立的測試後端，也沒有在正式環境實測。
- 派對島第一大陸的端對端測試使用「模擬七關通關資料＋遊戲原本的結算程式」，不是手動玩完七關。
- 派對島如果分好幾天、多次中斷才完成，伺服器場次只涵蓋最後一段，成績會進「待審核」由管理員決定。
- 每位玩家的 V幣帳本放在同一個節點：每天最多 4 筆，長期可接受；之後量大時再分頁封存。
- 排行榜讀取整個榜後在 Worker 排序：玩家數千人以內沒問題。
